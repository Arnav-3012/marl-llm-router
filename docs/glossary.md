# Glossary

Growing terminology reference. Every task adds the terms it introduces, in the same edit as its docs/viva.md entry (CLAUDE.md).

Written for a reader with NO prerequisite knowledge: each entry explains the idea from scratch, in plain words, before saying what it is in this project.

Entry format:
- **term (symbol)** — plain-English meaning, no assumed background.
- **Analogy:** an everyday picture of the mechanism.
- **Needs first:** other glossary terms to read before this one (only when useful).
- **Here:** what it means in this project (field, feature, config key, ADR).
- **More:** where to read more.

Rules for this file:
- Pointers only; no guide text is copied. A value that is not decided yet is never stated: the entry names the ADR or task that sets it.
- Toy numbers in an Analogy line are illustrations only, never project values (RULES.md #8).
- The Deep-Dive Learning Guide is not in the repo (docs/guide-errata.md). Guide references below are limited to part letters that the repo's own docs name: Parts A–B (learning gate L1, M0.5.0), Parts C–D (L2, M2.0), Part E (L3, M3.0), B1 (viva.md M0.1), C2, F1, F2, F3, G4, H4 (guide-errata.md). Where no part is named, only a docs or ADR pointer is given. Check part letters against the guide when it is next opened.
- When the guide and an ADR disagree, the ADR applies (docs/guide-errata.md).
- Symbol clashes to watch: **k** is the neighbour visibility radius (Multi-agent) and also the per-request batch coefficient in t_step(B) = t0 + k·B (LLM serving). **λ** is the cost dial in the reward, **λ_arr** the arrival rate and **λ_sat** the saturation rate. Context decides which; this file names them separately.

## Foundations

Words the rest of the file assumes. Read these first.

- **ADR (architecture decision record)** — a short written note recording one design decision, why it was made, and its status (Proposed / Accepted / Amended). **Analogy:** the minutes of a meeting: months later you can see what was decided and the reason, instead of guessing. **Here:** docs/decisions.md; RULES.md #7 says state, actions, reward, metrics and experiment design cannot change without one; each new ADR carries What and Why lines (RULES.md #14). **More:** docs/decisions.md.
- **agent** — a decision-maker that looks at its surroundings, picks an action, and gets feedback. **Analogy:** a shop-floor manager who sees only their own section, decides what to do with each incoming job, and later hears whether it went well. **Here:** one agent per server; N agents in total. **More:** docs/context.md Agent; ADR-002.
- **baseline** — a simple, known method you compare your new method against. If the new method cannot beat it, it is not worth it. **Analogy:** a runner's previous personal best. **Here:** the heuristics (Random, Round-robin, JSQ, Po2, SED, Cache-aware); they run on exactly the same traffic as the learned agents (CLAUDE.md). **More:** docs/context.md Baselines; ADR-012.
- **calibration (and profiling)** — profiling means measuring how a real system behaves (here: timing real LLM servers). Calibration means feeding those measurements into the simulator so it behaves like the real thing. **Analogy:** weighing real ingredients before writing a recipe, instead of guessing amounts. **Here:** profiling/calibration.json is the only allowed source of server parameters (RULES.md #8); many config values are `null` until calibration fills them in (M0.5). **More:** docs/context.md Environment; ADR-003; M0.5.
- **config (YAML)** — a plain text file of settings (name: value pairs) that code reads, so numbers are not hard-coded in the program. YAML is the file format. **Analogy:** the dials on a machine, kept on a panel outside the machine. **Here:** configs/*.yaml. Rule: config + seed → identical output; no magic numbers in code (CLAUDE.md). A value of `null` means "not decided yet". **More:** CLAUDE.md Engineering rules.
- **discrete-event / discrete-time simulation** — a program that imitates a real system by advancing a clock in steps and updating the state at each step, instead of running the real system. **Analogy:** a board game that models a city's traffic: each turn, cars move, and you can replay or speed it up. **Here:** the cluster simulator advances in ticks (see **tick**). Cheap and fast, so agents can practise millions of decisions that would take days on real servers. **More:** docs/context.md Environment; docs/architecture.md sim.
- **gradient / gradient descent** — a gradient tells you, for each adjustable number in a model, which direction increasing it would change the error. Gradient descent nudges every number a little in the direction that lowers the error, over and over. **Analogy:** walking downhill blindfolded by feeling the slope under your feet. **Needs first:** loss, parameters. **Here:** this is how the Q-network is trained; Adam is a smarter version, and gradient clipping caps a too-large step. **More:** Guide Parts C–D.
- **GPU / CPU** — CPU: the general-purpose processor, good at doing a few complicated things in sequence. GPU: a processor with thousands of small cores, good at doing the same simple maths on huge arrays at once (what neural networks need). **Here:** LLM servers use the GPU (Metal on the Mac); Docker on macOS cannot reach it, hence the `cpu` and `host` compose profiles; the demo runs on a CPU. torch device: mps if available, else cpu (CLAUDE.md). **More:** ADR-007.
- **heuristic** — a hand-written rule of thumb that gives a good-enough answer without learning anything. **Analogy:** "always join the shortest supermarket queue". **Here:** each baseline is a heuristic; see "heuristic, local vs global". **More:** ADR-012.
- **latency vs throughput** — latency: how long ONE request takes. Throughput: how many requests the system finishes per second. They pull against each other: cramming more work in raises throughput but each item waits longer. **Analogy:** a restaurant: latency is how long your meal takes; throughput is how many tables it serves per hour. **Here:** the SLA is about latency; goodput is a throughput measure that only counts good-enough requests. **More:** docs/context.md Metrics.
- **loss** — one number measuring how wrong the model currently is; training tries to make it small. **Analogy:** the score in golf, lower is better. **Here:** the TD loss with a Huber shape (see RL). **More:** Guide Parts C–D.
- **neural network and parameters (weights)** — a neural network is a function made of layers of simple arithmetic; its parameters (weights) are the thousands of numbers inside it that training adjusts. **Analogy:** a huge mixing desk with many knobs; training turns the knobs until the output sounds right. **Here:** each agent has a small network (the MLP 7→64→64→3) mapping 7 numbers describing the situation to 3 scores, one per action. **More:** docs/architecture.md agents.
- **observation vs state** — state is the true full situation of the world; an observation is the part a given agent actually gets to see. **Analogy:** a poker player sees their own cards, not the whole table's. **Here:** each agent sees 7 numbers, never the full cluster (partial observability). **More:** docs/architecture.md Observation; ADR-013.
- **policy** — the rule an agent follows to turn what it sees into an action. **Analogy:** the playbook. **Here:** a learned policy comes from the Q-network (take the action with the highest Q); a heuristic is a hand-written policy. **More:** docs/architecture.md policies.
- **probability distribution** — a description of how likely different values are. **Analogy:** a histogram of how tall people are: most near the middle, few at the extremes. **Here:** prompt and output lengths in the traces are far from bell-shaped (a few huge requests), which is why percentiles matter more than averages. **More:** docs/phase-plans.md M0.3.
- **queue** — a line of requests waiting for a server to become free. **Analogy:** the checkout line. **Here:** each server holds work; waiting time in it counts toward TTFT. **More:** Queueing section.
- **random seed** — a starting number for a random number generator. Same seed gives the exact same "random" sequence, so an experiment can be repeated exactly. **Analogy:** a shuffled deck whose order you can recreate by naming the shuffle. **Here:** every run takes a seed; different seeds test that a result is not a lucky shuffle (≥ 5 seeds). **More:** CLAUDE.md Engineering rules; M4.2.
- **reinforcement learning (RL)** — learning by trial and error: act, receive a reward (a score), adjust to get more reward in future. No one provides the right answer; the agent discovers it. **Analogy:** training a dog with treats. **Here:** the whole project is RL on top of a simulator. **More:** docs/context.md; Guide Parts C–D.
- **request** — one user's call to an LLM: a prompt in, generated text out. **Here:** the Request object (sim/request.py) carries prompt tokens, output tokens, SLA targets, hop count and optionally a conversation id. **More:** docs/architecture.md sim.request.
- **server** — a machine (or program on one) that does work on demand. **Here:** each simulated server stands for one LLM running on a GPU, with its own speed, memory and price (server class). **More:** docs/context.md Environment.
- **tensor / vector** — a vector is a list of numbers; a tensor is a grid of them (any number of dimensions). **Here:** an observation is a vector of 7 numbers; a replay batch is a tensor. **More:** docs/architecture.md agents.

## LLM serving

How a real LLM server spends its time. The simulator models this with a small formula.

- **a (prefill cost per token)** — how many seconds the server spends reading each prompt token it has not seen before. **Analogy:** a reader's speed in seconds per page, for pages not already read. **Needs first:** prefill, token. **Here:** the `a` in T = a·(P − P_cached) + Σ t_step(B_i); fitted per server class into profiling/calibration.json (configs/servers.yaml `prefill_cost_per_token`, null until M0.5.5). Never hand-picked (RULES.md #8). **More:** docs/context.md Environment; ADR-003; Guide Parts A–B; M0.5.4.
- **batch size (B)** — how many requests the server is generating text for at the same moment. **Analogy:** a bus: carrying more passengers per trip is more efficient overall, but each trip is a bit slower. **Needs first:** decode. **Here:** B_i is the batch in decode step i; it enters t_step(B) and is how each decode step's cost is split across requests (ADR-014). **More:** docs/context.md Environment; ADR-014; Guide Parts A–B.
- **cache speedup** — how much faster prefill gets when part of the prompt is already cached. **Analogy:** not re-reading the first chapters of a book you read yesterday. **Needs first:** prefix cache. **Here:** a per-class parameter from calibration.json (configs/servers.yaml `cache_speedup`), used with P_cached. **More:** ADR-003; M0.5.4; Guide Parts A–B.
- **continuous batching** — instead of waiting for a whole group of requests to finish, the server lets new requests join and finished ones leave between every single output step. **Analogy:** a bus that picks up and drops off passengers at every stop, rather than only at the depot. **Needs first:** batch size, decode. **Here:** the reason service time is a sum over decode steps whose cost depends on the current B; the project models only t_step = t0 + k·B, not batching internals (out of scope, docs/context.md). **More:** docs/context.md Environment and Constraints; Guide Parts A–B.
- **decode** — the phase where the model writes its answer one token at a time; each new token needs one full pass through the model. **Analogy:** writing a sentence word by word, each word depending on all the words before. **Here:** the Σ t_step(B_i) term of service time, one step per output token; its speed is what TPOT measures. **More:** docs/context.md Environment; Guide Parts A–B.
- **E2E (end-to-end latency)** — total time from a request arriving to its last output token. **Analogy:** door-to-door travel time, not just the flight. **Here:** reported in the Latency metrics group (docs/context.md Metrics); not itself an SLA target (the targets are TTFT and TPOT). Computed in sim/metrics.py (M1.20). **More:** docs/context.md Metrics; Guide Parts A–B.
- **GGUF and Q4_K_M** — GGUF is the file format llama.cpp uses to store a model. Quantisation stores the model's numbers with fewer bits (Q4 means about 4 bits each) so the file is smaller and faster, at a small quality cost. **Analogy:** a JPEG: smaller than the original, slightly lossy, usually fine. **Here:** the real fast-class server runs Qwen2.5-3B in this form (configs/servers.yaml `real_model`); the slow-class model is decided in M0.5. **More:** docs/context.md Environment; M0.5.1.
- **interference** — extra slowdown a request suffers because other requests share the same server. **Analogy:** a shared kitchen: each cook is slower when others are using the same stove. **Here:** a per-class calibration parameter (configs/servers.yaml `interference`, null until calibration); its exact role in the service-time formula is fixed when sim/server.py is built (M1.7–M1.8). **More:** docs/context.md Environment; ADR-003.
- **KV cache** — while generating, the model keeps a stored summary (the "keys" and "values" of attention) for every token already processed, so it does not recompute them. It grows with every token and uses memory. **Analogy:** your desk: notes about everything read so far; the more you read the fuller the desk, and when it is full you cannot take another job. **Needs first:** token. **Here:** modelled as a token budget per server (sim/kv_cache.py: admit, release, fullness). Observation feature "own KV fullness". **More:** docs/architecture.md sim.kv_cache; M1.3–M1.4; Guide Parts A–B.
- **KV token budget (capacity)** — the maximum number of tokens a server's KV cache can hold; sets how much work it can hold at once. **Here:** "Capacity = KV token budget" (docs/context.md); configs/servers.yaml `kv_token_budget` from calibration.json. The 80% fullness threshold for the KV reward term is in ADR-014. **More:** docs/context.md Environment; ADR-014.
- **llama-server (llama.cpp)** — open-source program that runs LLMs on ordinary computers and exposes them over HTTP. **Here:** the source of real timings for calibration (M0.5) and the real backend for the M6 router. **More:** docs/context.md Environment and Pipeline; M0.5.1, M6.1.
- **Metal** — Apple's interface for using the Mac's GPU. **Here:** the fast class runs on Metal; Docker on macOS cannot use it, hence the `host` compose profile. **More:** ADR-007; docs/context.md Showcase spec.
- **prefill** — the first phase: the server reads the entire prompt in one go before writing any output. **Analogy:** reading the question fully before you start answering. Long prompts mean a long wait before the first word appears. **Here:** the a·(P − P_cached) term of service time; it dominates TTFT for long prompts. **More:** docs/context.md Environment; Guide Parts A–B.
- **prefix cache** — if a new prompt begins with text the server has already processed (e.g. the earlier turns of a chat), it reuses the stored work for that beginning and only processes the new part. **Analogy:** a bookmark: resume from where you left off instead of from page 1. **Needs first:** KV cache, prefill. **Here:** sim/prefix_cache.py (hit_tokens, insert); needs a conversation id so a follow-up turn can match a server that holds its prefix (ADR-009). Cache variant adds the prefix-hit fraction to the observation. Capacity is a constructor argument; its value is not decided yet. **More:** ADR-009; docs/architecture.md sim.prefix_cache; M1.5–M1.6.
- **Qwen2.5** — an open family of LLMs from Alibaba. **Here:** Qwen2.5-3B Q4_K_M for the fast class (configs/servers.yaml); "3B" means about 3 billion parameters. **More:** docs/context.md Environment.
- **service time (T)** — how long a server needs to fully handle one request (prefill plus all decode steps), not counting time spent waiting in line. **Needs first:** prefill, decode. **Here:** T = a·(P − P_cached) + Σ t_step(B_i): "a times the new prompt tokens, plus the sum of the decode step times". Parameters only from calibration.json. The estimate of this value for a specific neighbour is part of the Forward-target rule (ADR-013). **More:** docs/context.md Environment; ADR-003, ADR-013; M1.7–M1.8.
- **SLA (service-level agreement)** — the latency promise a request must meet. **Analogy:** a pizza guaranteed within 30 minutes. **Here:** a request meets its SLA when it meets both its TTFT target and its TPOT target; R_SLA is +10 if met, −10 if a target is missed, −5 if dropped (ADR-010). Values of the targets: see "TTFT/TPOT target". **More:** docs/context.md Agent; ADR-010.
- **step time (t_step(B), t0, k)** — time of ONE decode step when B requests are in the batch. The formula t_step(B) = t0 + k·B says: a fixed base time t0, plus k extra seconds for each request in the batch. **Analogy:** a lift trip: fixed time to go up, plus a little per person to get in and out. Edge cases: B = 1 gives t0 + k; larger B makes each step slower but serves more people per step. **Here:** t0 and k come only from calibration.json (configs/servers.yaml `step_base_time`, `step_per_batch_time`). This k is not the visibility radius. **More:** docs/context.md Environment; ADR-003; M0.5.4.
- **token** — the chunk of text an LLM actually reads and writes, usually a word or part of a word ("unhappiness" may be 2–3 tokens). Everything (length, memory, speed, cost) is counted in tokens. **Here:** P and O are token counts; the KV budget is in tokens; TPOT is seconds per output token. **More:** docs/context.md Environment; Guide Parts A–B.
- **TPOT (time per output token)** — the average gap between consecutive output tokens after the first; how fast the text "streams". **Analogy:** reading speed of a typist once they have started. **Here:** one of the two SLA targets and reported as p50/p95 (p99 if enough requests). **More:** docs/context.md Metrics; Guide Parts A–B.
- **TTFT (time to first token)** — how long you wait before the first word of the answer appears: queueing wait plus prefill. **Analogy:** the pause before someone starts speaking after you ask a question. **Here:** one of the two SLA targets; time spent held by an agent waiting for its turn counts toward it (ADR-013). **More:** docs/context.md Metrics; ADR-013; Guide Parts A–B.
- **TTFT/TPOT target** — the per-request thresholds that define "SLA met" (e.g. first token within X seconds, then at most Y seconds per token). **Here:** fields `ttft_target`, `tpot_target` on the Request and `sla.*` in configs/sim.yaml. Values are not decided: set by ADR in M1.2, from calibration and EDA. ADR-011 keeps λ_sat independent of them. **More:** docs/phase-plans.md M1.2; ADR-011; docs/architecture.md sim.request.

## Queueing

The maths of waiting in line. It explains why a busy cluster gets slow so suddenly.

- **arrival rate (λ_arr)** — how many new requests come in per second on average. **Analogy:** customers walking into a shop per minute. **Here:** the stream sampler takes λ_arr in req/s, not ρ (M0.6); ρ is converted to λ_arr in M1.28. **More:** ADR-011; docs/phase-plans.md M0.6, M1.28; Guide H4.
- **backlog** — requests that have arrived but are not finished yet (waiting plus being served). **Analogy:** the pile in your inbox. If the pile keeps growing the system is overloaded. **Here:** the third λ_sat criterion compares in-system count in the last quarter of the arrival window against the second quarter (ADR-011). Held-but-waiting requests also show up as TTFT (ADR-013). **More:** ADR-011, ADR-013.
- **expected wait (Ŵ)** — an estimate of how long a newly accepted request would wait before service on a server. **Here:** the observation feature "own expected wait" and the `Server.expected_wait()` interface; used for SED-style rules and the Forward target. The exact formula is fixed in M1.7–M1.8, not here. **More:** docs/architecture.md sim.server; ADR-012, ADR-013.
- **FIFO** — first in, first out: the oldest item is handled first. **Analogy:** a queue at a bakery. **Here:** an agent decides on the oldest request it holds each tick; a deferred request goes to the back (ADR-013). **More:** ADR-013.
- **inter-arrival CV (c_a)** — a burstiness score. Take the gaps between consecutive arrivals; divide their standard deviation (how spread out they are) by their mean (their average). Exactly steady-random traffic (a Poisson process) gives 1; traffic that comes in clumps gives more than 1. **Analogy:** rain that falls steadily vs in sudden downpours. **Here:** a burstiness measure from the trace EDA (M0.3); whether it becomes a reported or configured quantity is not decided. **More:** docs/phase-plans.md M0.3; BurstGPT entry below.
- **Little's law (L = λ_arr · W)** — in a steady system, the average number of requests inside (L) equals the arrival rate (λ_arr) times the average time each spends inside (W). **Analogy:** a shop that gets 2 customers per minute who each stay 10 minutes holds about 20 people. It holds whatever the details of the shop. **Here:** a simulator sanity check at ρ = 0.5 and 0.8 (M1.30 (ii)): if the simulator breaks this law, it has a bug (a lost or double-counted request). **More:** docs/phase-plans.md M1.30.
- **Poisson process** — the textbook model of random arrivals: each arrival is independent of the others, gaps are exponentially distributed, rate constant. "Memoryless": knowing how long since the last arrival tells you nothing about the next. **Here:** the reference against which trace burstiness (c_a) is judged; our traffic comes from real traces, not a Poisson generator. **More:** docs/context.md Environment; docs/phase-plans.md M0.3.
- **ρ and λ_sat (load and saturation rate)** — λ_sat is the arrival rate at which the whole cluster just manages to keep up; any faster and the backlog grows without bound. ρ = λ_arr / λ_sat is the load as a fraction of that: ρ = 0.5 means half the maximum, ρ near 1 means on the edge. **Analogy:** a motorway's capacity: at 50% of capacity traffic flows; near 100% one braking car causes a jam. **Here:** λ_sat is measured on the global-form SED cluster by completion ratio, drop rate and backlog growth, per trace and cache setting; the thresholds are stated assumptions. ρ ∈ {0.5, 0.8, 0.95} in experiments. The λ_sat value is not known yet: measured in M1.26–M1.28, then recorded in ADR-011. Replaces the guide's λ/Σμ. **More:** ADR-011; docs/guide-errata.md; Guide H4.
- **slack** — how much time is left before a request's target would be missed. **Analogy:** how many minutes to spare before a train leaves. **Here:** the observation feature "slack on this server" (docs/architecture.md); the exact formula is fixed with the observation builder (M1.14–M1.15). E6 analyses slack of accepted requests by server class. **More:** docs/architecture.md Observation; docs/context.md Experiments (E6).

## Data and traces

Where the simulator's traffic comes from.

- **Azure LLM Inference Trace 2023** — a public log of real LLM requests from Microsoft Azure: when each arrived, how many prompt tokens, how many generated tokens. No text, no user data. **Here:** the main traffic source (`traffic.source: azure2023`); it carries no conversation id (ADR-009). Collected 2023-11-11 per data/README.md. **More:** data/README.md; configs/data.yaml; ADR-009; Guide B1.
- **BurstGPT** — a public log of real LLM usage with very bursty arrivals; the v2.0 file includes a Session ID. **Here:** burst tests (E5) and, possibly, conversation structure; BurstGPT_3 is needed for Session ID, BurstGPT_1 has none (docs/viva.md M0.1). **More:** data/README.md; configs/data.yaml; ADR-009; Guide B1.
- **ContextTokens / GeneratedTokens** — the Azure trace's column names for prompt length and output length. **Here:** they become P and O (prompt tokens, output tokens) of a Request. BurstGPT's equivalents are Request tokens and Response tokens. **More:** data/README.md; docs/architecture.md data.traces.
- **conversation id** — a label shared by all requests in one chat, so the system can tell a follow-up from a fresh question. **Why it matters:** a follow-up repeats the earlier turns, so a server that already holds them can skip that work (prefix cache). **Here:** Request.conv_id; the source (BurstGPT Session ID or synthetic sessions over Azure) is undecided: ADR-009 is proposed until the M0.3 findings. **More:** ADR-009; docs/context.md Environment.
- **conversation mode (BurstGPT)** — BurstGPT rows that came from chat sessions, as opposed to one-shot API calls. **Here:** only conversation-mode rows have a Session ID, so only they can support real prefix-cache structure. How large that subset is: found in M0.3 (ADR-009). **More:** docs/viva.md M0.1; ADR-009; data/README.md.
- **EDA (exploratory data analysis)** — looking at the data (plots, summaries, percentiles) before building anything, to learn its shape and traps. **Here:** M0.3 on the traces; its findings decide ADR-009 and several config values. **More:** docs/phase-plans.md M0.3.
- **held-out traffic** — a part of the trace kept completely separate and never used for training or tuning, so the final test is honest. **Analogy:** the exam questions the student has never seen. **Here:** all reported evaluation uses it, with ε = 0 and at least 5 seeds; tuning uses train traffic only. **More:** docs/context.md Metrics; CLAUDE.md Engineering rules; M2.11.
- **normalisation constants** — per-feature scales that squeeze raw values (which could be tiny or huge) into the range 0 to 1, so a neural network treats all features fairly. **Here:** 99th percentile per feature, clipped to [0, 1] (anything above the 99th percentile counts as 1), written to data/processed/normalisation.json (M0.4); the observation builder uses them (M1.14). **More:** docs/architecture.md data.processed; docs/phase-plans.md M0.3.1, M0.4.
- **prompt tokens (P), output tokens (O)** — token counts of a request's input and generated output. **Here:** Request.prompt_tokens, Request.output_tokens; P_cached is the part of the prompt served from the prefix cache. **More:** docs/context.md Environment; docs/architecture.md sim.request.
- **Session ID** — BurstGPT column grouping requests of one chat session. **Here:** candidate source of conversation id; present only in BurstGPT_3 and only for conversation-mode rows. Fraction of rows with one: measured in M0.1/M0.3. **More:** ADR-009; configs/data.yaml; docs/viva.md M0.1.
- **stream sampler** — code that turns a trace into a seeded stream of Requests at a chosen arrival rate (speeding the trace up or slowing it down). **Here:** data/traces.py `sample_stream(trace, rho, seed, split)` in the architecture; per M0.6 it takes a rate in req/s and the same seed gives the same stream. **More:** docs/architecture.md data.traces; docs/phase-plans.md M0.6.
- **train/held-out split** — a time-ordered division of the trace: the earlier part for training, the later part for evaluation, no overlap. Time-ordered so the agent cannot peek at the future. **Here:** `traffic.train_split` in configs/sim.yaml (null until M0); built in data/processed.py (M0.4). **More:** docs/phase-plans.md M0.3.1, M0.4.

## RL

The learning machinery, from scratch. Read in this order: reward → return → Q-value → replay buffer → target network → Double DQN.

- **action histogram** — a count of how often each action is chosen. **Why it matters:** an agent that picks one action 100% of the time has stopped thinking (a "degenerate policy"). **Here:** a training-health metric and a gate in M2.12 (more than one action in use). **More:** docs/context.md Metrics; docs/guide-errata.md (G4); docs/phase-plans.md M2.12.
- **action mask** — a yes/no list marking which actions are allowed right now; forbidden ones are never chosen. **Analogy:** greying out menu items that are unavailable. **Here:** mask[3] over Accept, Forward, Defer; Forward is masked at k = 0 and at the hop limit, Defer at the defer limit; no legal action means the request is dropped. Break-it (d) removes masking. **More:** ADR-013; docs/architecture.md; M2.16.
- **Adam / Huber loss / gradient clipping** — three training stabilisers. Adam: an optimiser that adapts the step size for each parameter. Huber loss: treats small errors like squared error but large errors only linearly, so one wild outlier does not wreck training. Gradient clipping: if the update step would be enormous, shrink it to a maximum size. **Analogy:** careful driving: smooth steering, no slamming the brakes, a speed limiter. **Needs first:** gradient, loss. **Here:** the optimiser and loss in configs/dqn.yaml (`loss: huber`, `optimizer: adam`, `grad_clip`); learning rate and batch size are not decided: set by ADR in M2.11. **More:** docs/context.md Agent; configs/dqn.yaml; Guide Parts C–D.
- **discount (γ)** — how much a future reward is worth compared with one now. A reward t decisions away counts γ^t times as much. **Analogy:** "a bird in the hand": γ = 0 is totally short-sighted, γ near 1 is patient. **Here:** γ = 0.99 in configs/dqn.yaml, applied once per decision, not per tick (ADR-010). Break-it (c) compares γ ∈ {0, 0.9, 0.99}. **More:** ADR-010; M2.15; Guide Parts C–D.
- **Double DQN** — DQN is Deep Q-Network: a neural network that predicts the Q-value of each action. Plain DQN tends to over-estimate Q-values, because it both picks the best-looking action and scores it with the same, noisy, network. Double DQN splits the job: the online network picks the action, the target network scores it. **Analogy:** one person nominates a candidate, a different person grades them, so a lucky over-score is less likely. **Needs first:** Q-value, target network. **Here:** each agent is an independent Double DQN (MLP 7→64→64→3). **More:** ADR-002; M2.5–M2.7; Guide Parts C–D.
- **epsilon (ε, ε-greedy)** — with probability ε the agent ignores its network and acts randomly, so it keeps exploring; otherwise it takes the best-looking action. **Analogy:** sometimes trying a new restaurant instead of your favourite. ε = 1 is pure random; ε = 0 is pure greedy. **Here:** ε decays from 1.0 to 0.05 in training (configs/dqn.yaml; decay length not decided: set by ADR in M2.11); evaluation uses ε = 0 (no exploring when we measure). **More:** docs/context.md Agent and Metrics; M2.6, M2.11.
- **MLP** — multilayer perceptron: the plainest neural network, layers of weighted sums with a simple non-linearity (ReLU) between. **Here:** the Q-network 7→64→64→3 with ReLU: 7 inputs, two hidden layers of 64, 3 outputs (agents/networks.py). **More:** docs/architecture.md agents; M2.1–M2.2.
- **Q-value (Q, mean Q)** — the network's estimate of the total future reward if it takes this action now and behaves well afterwards. **Analogy:** a chess player's gut rating of each move. **Here:** QNetwork outputs three Q-values per observation (Accept, Forward, Defer); mean Q is a training-health metric. **More:** docs/context.md Metrics; Guide Parts C–D.
- **replay buffer** — a memory holding past experiences (transitions); training picks random samples from it. **Why:** consecutive experiences are near-copies of each other; shuffling them gives the network a varied diet and uses each experience many times. **Analogy:** studying from shuffled flash cards instead of re-reading the same chapter. **Here:** per-agent buffer, capacity set in configs/dqn.yaml (context.md range 20–50k); warmup is not decided: set by ADR in M2.11. Break-it (b) removes it. **More:** docs/architecture.md agents; M2.3–M2.4, M2.14.
- **return** — the (discounted) sum of rewards over an episode: the total score for one run. **Here:** a training-health metric logged per episode. **More:** docs/context.md Metrics; M2.10.
- **reward (r)** — the number telling an agent how good its decision was. **Analogy:** a treat or a scolding. **Here:** per decision transition: shared R_SLA at resolution − λ·C (serving agent) − KV term (serving agent) − β·B_t (every transition) − immediate Defer/Forward costs (values set by a later ADR). **More:** docs/context.md Agent; ADR-010, ADR-014; Guide F3.
- **s′ (next state)** — the observation the agent gets at its next decision after the one that produced the transition. **Here:** not the state at the resolution tick (option (a) was withdrawn); the DDQN target uses γ once per decision. **More:** ADR-010; docs/architecture.md agents.
- **target network** — a frozen, slowly updated copy of the Q-network used to compute the numbers the online network is trained towards. **Why:** without it the network chases a target that moves every time it learns, which makes training unstable. **Analogy:** studying against last week's answer key instead of one rewritten every minute. **Here:** part of each DDQN agent; sync rule not decided: set by ADR in M2.11. Break-it (a) removes it. **More:** docs/context.md Agent; M2.7, M2.13; Guide Parts C–D.
- **TD loss** — temporal-difference loss: the gap between what the network predicted for an action and what actually happened (reward plus discounted estimate of what comes next), passed through the Huber loss. **Analogy:** "I expected 5 points, I got 3 and the next position looks worth 1, so I was off by 1". **Here:** a training-health metric. **More:** docs/context.md Metrics; M2.7.
- **transition** — one record of experience: what the agent saw, what it did, what reward it got, and what it saw next. **Here:** Transition(obs[7], mask[3], action, decision tick, reward, next obs[7], next mask[3], truncated); it is pushed to the replay buffer only when both its reward (at resolution) and its s′ (next decision) exist. **More:** ADR-010; docs/architecture.md agents.
- **truncation vs termination** — termination: the process truly ends, so no future reward exists. Truncation: we cut the run off for practical reasons, so the future would have had value and the target must still look ahead (bootstrap). **Analogy:** a game that ends because someone won (termination) vs the clock being stopped at full-time while play was ongoing (truncation). **Here:** the episode end is truncation: arrivals stop at `episode_ticks`, the cluster drains, then training ends; unresolved requests at the drain horizon count as dropped. Values of the horizon: set in configs/. **More:** ADR-010; M1.2.

## Multi-agent

Several learners at once, each seeing only part of the picture.

- **β and B_t (cooperation term)** — B_t is the cluster-wide breach rate over a recent window of time; β is how strongly its penalty is weighted. Adding −β·B_t to everyone's reward means each agent feels the whole cluster's failures, not only its own. **Analogy:** a team bonus that depends on the whole team's results. **Here:** reward term on every transition, B_t sampled at the transition's decision tick (ADR-014). `beta_coop` is 0.0 in configs/sim.yaml (off); the β value and the window W are not decided: set by ADR in M3.5. E2 compares on and off. **More:** ADR-014; docs/phase-plans.md M3.3–M3.5; Guide C2, F3.
- **centralised DQN** — a single DQN that sees every server at once and decides for all of them together. **Why it is the reference:** it has the most information, so it should do at least as well; the gap to the independent agents shows what decentralisation costs. **Here:** the reference upper bound for E4; the joint-action design is a Proposed ADR in M3.8. **More:** ADR-002; docs/phase-plans.md M3.8–M3.10; Guide Part E.
- **credit assignment** — working out which agent and which action deserves the praise or blame for an outcome. **Analogy:** a late delivery: was it the warehouse, the driver, or the dispatcher? **Here:** shared R_SLA goes to every agent that acted on a request; cost and KV terms go to the serving agent only; outcomes are credited at resolution with decision-time state. **More:** ADR-004, ADR-010, ADR-014; Guide F3.
- **independent learners** — each agent trains its own network and treats the other agents as part of the weather. **Here:** N = 4 independent DDQN agents with per-agent buffers and rewards (M3.2). **More:** ADR-002; Guide Part E.
- **k (visibility radius)** — how far an agent can see its neighbours. k = 0 sees nobody, k = 1 sees the nearest ones, "full" sees all. **Here:** `observation.k` in configs/sim.yaml (E4 sweeps); at k = 0 the neighbour feature is 0 and Forward is masked. Not the batch coefficient k in t_step. **More:** docs/context.md Agent; docs/architecture.md Observation; ADR-013; M3.6–M3.7.
- **neighbour mean wait** — the average expected wait of the servers within radius k; the only neighbour information an agent gets, one number, not a per-server list. **Here:** observation feature 6 (0 when k = 0). Local heuristics can use only this mean, never per-neighbour values (ADR-012). **More:** docs/architecture.md Observation; ADR-012; M3.7.
- **non-stationarity** — from one agent's point of view the world keeps changing, because the other agents are learning and changing their behaviour. **Analogy:** learning chess against an opponent who improves every game. **Why it matters:** standard RL theory assumes a fixed world, so independent learning has no guarantee; it often works anyway. **Here:** accepted cost of independent learning (ADR-002); break-it (f) and (g) probe it. **More:** ADR-002; M3.14–M3.15; Guide Part E.
- **observation (7 features)** — what one agent sees each decision, all scaled to [0, 1]: own expected wait, own KV fullness, prompt size, slack on this server, hop count, neighbour mean wait, prefix-hit fraction. **Here:** replaces the guide's 6 features; an idle agent gets 7 zeros and an all-False mask. **More:** docs/architecture.md; ADR-013; docs/guide-errata.md; Guide F1.
- **ParallelEnv (PettingZoo)** — a standard interface for multi-agent environments: all agents act at the same time, and `reset` and `step` return a dictionary with one entry per agent. PettingZoo is the library defining it. **Here:** the shape of sim/cluster.py; pettingzoo is a dev dependency used only for an API-shape test. **More:** ADR-005; docs/architecture.md sim.cluster.
- **partial observability** — each agent sees only part of the true state. **Analogy:** driving in fog. **Here:** the price of it is measured by E4 (k = 0, 1, full against centralised DQN). **More:** docs/context.md Questions (3); ADR-002; Guide Part E.
- **VDN and CTDE** — value decomposition networks learn a joint Q-value as the sum of per-agent Q-values; CTDE (centralised training, decentralised execution) is the family: use global information while training, but each agent acts on local information. **Here:** out of scope; VDN is future work. **More:** docs/context.md Constraints; ADR-002.

## Metrics

How results are judged. Every number needs ≥ 5 seeds, ε = 0, held-out traffic.

- **breach rate** — the fraction of requests that miss an SLA target. **Here:** an outcome metric; B_t in the cooperation term is the cluster breach rate over the last W steps. How drops count in it is fixed in M1.19 and M3.3. **More:** docs/context.md Metrics; ADR-014; M3.3.
- **cache hit rate** — how much of the prompt work was saved by the prefix cache. **Here:** an outcome metric; the exact definition is fixed in sim/metrics.py (M1.19–M1.20) and is validated on real conversation structure only per ADR-009. **More:** docs/context.md Metrics; ADR-009.
- **cost per request** — the average money-like cost of serving a request. **Here:** equals the reward's cost term before the λ weight, with the invariant Σ_j C_j = Σ_i c_i × busy_seconds_i (total cost over requests equals price times busy seconds over servers; tested in M1.17); class prices not decided: set by ADR in M0.5.6. **More:** ADR-014; docs/architecture.md sim.metrics.
- **drop rate** — the fraction of requests that end as dropped (never served properly). **Here:** outcome metric and one λ_sat criterion (> 1%, an assumption). A drop counts against the last holder in per-server metrics. **More:** ADR-010, ADR-011, ADR-013.
- **goodput** — throughput that counts only the requests that were good enough: requests per second that met their SLA. **Analogy:** a factory counting only the products that pass quality control. **Why headline:** raw throughput can look great while most requests are late. **Here:** the exact definition is fixed in sim/metrics.py (M1.19–M1.20), not here. **More:** docs/context.md Metrics; M1.19.
- **Jain's index** — a fairness score, (Σx)² / (n·Σx²), where x is each server's share of something (e.g. load) and n the number of servers. It runs from 1/n (one server does everything) to 1 (perfectly even). **Example idea:** equal shares give 1; one server with everything gives 1/n. **Here:** reported as an outcome metric; the quantity it is computed over is fixed in M1.19–M1.20. **More:** docs/context.md Metrics; docs/phase-plans.md M1.19.
- **mean ± 95% CI** — the average over seeds, plus an interval showing how much it might wobble: a 95% confidence interval says "if we repeated the whole experiment many times, intervals built this way would contain the true average about 95% of the time". Narrow interval: reliable; wide: noisy, so do not trust small differences. **Here:** every reported number uses at least 5 seeds, ε = 0, held-out traffic; one seed is never reported, and the best seed is never picked. `mean_ci95` in eval/stats.py; the method is fixed in M4.1–M4.2. **More:** CLAUDE.md Engineering rules; docs/architecture.md eval; M4.2.
- **Pareto frontier** — among results with two goals that conflict (here cost and latency), the set of results where you cannot improve one without worsening the other. Everything else is "dominated". **Analogy:** flights: you cannot find a cheaper AND faster one among the frontier flights. **Here:** (cost, latency) points from the λ sweep in E3; `pareto_front` returns the non-dominated indices. Question 2 asks whether learned agents trace a frontier that fixed rules cannot. **More:** docs/context.md Questions (2) and Experiments (E3); docs/architecture.md eval; M4.3–M4.4.
- **percentiles (p50, p95, p99)** — the value below which 50%, 95% or 99% of requests fall. p50 is the median (the typical request); p95 is "the slow end that 1 in 20 requests reaches". **Why not the average:** a few very slow requests hide inside an average but show up at p95/p99. **Here:** TTFT and TPOT are reported at p50 and p95, and p99 only if there are enough requests. **More:** docs/context.md Metrics; M1.19.
- **SLA attainment** — the fraction of requests that meet both targets. **Here:** outcome metric, also recorded at 0.1 × λ_sat to show the targets are achievable at all (at low load, nearly everything should pass). **More:** docs/context.md Metrics; ADR-011.
- **sim-to-real gap** — how far the simulator's answer is from the real system's: |sim − real| / real, as a relative error. **Why it matters:** a simulator that disagrees with reality proves nothing about the real router. **Here:** E7, computed for SED first, then the learned policy and cache-aware. **More:** docs/context.md Metrics; M6.9–M6.10.
- **utilisation** — the share of time a server is busy. **Here:** outcome metric from `Server.busy_seconds`; the exact denominator is fixed in M1.20. **More:** docs/context.md Metrics; docs/architecture.md sim.server.

## Project-specific

The router's own vocabulary: the three actions, the heuristics and the reward terms.

- **Accept (action 0)** — the agent that holds the request serves it on its own server. **Here:** one of Accept, Forward, Defer; it is the transition that carries the cost and KV terms (ADR-014). **More:** docs/architecture.md Actions; ADR-014.
- **Cache-aware (baseline)** — a heuristic that prefers servers that already hold the start of this request's prompt, while penalising busy ones. **Here:** score = overlap − w·load; local and global forms; the local rules and masked-action fallback are written in the ADR-012 amendment (M1.21), and the weight w is not decided. **More:** docs/context.md Baselines; ADR-012; M1.25.
- **cost (C) and cost dial (λ)** — C is the money-like cost of serving a request; λ (lambda) is the dial that weights it against the SLA reward. Turn λ up and agents become frugal (cheap slow servers), turn it down and they chase speed. **Here:** C_j = class price × service seconds attributed to j (prefill in full, each decode step split across the batch), charged at resolution to the serving agent. `lambda_cost` default is 0.5 in configs/sim.yaml; E3 sweeps λ ∈ {0, 0.25, 0.5, 1, 2}. Not λ_arr or λ_sat. **More:** ADR-014; docs/context.md Experiments (E3); Guide F3.
- **defer (D)** — the action "not now, ask me again later". **Analogy:** "take a number and sit down". **Here:** action 2; a deferred request moves to the back of the agent's queue (ADR-013); masked at the defer limit D (`max_defers`). D is not decided: set by ADR in M1.2 (configs/sim.yaml `max_defers: null`). The immediate cost of Defer is set by a later ADR (ADR-010). **More:** ADR-013, ADR-010; docs/architecture.md.
- **drop** — a request that ends with no legal action, or is still unresolved at the drain horizon. Counted as a failure. **Here:** R_SLA −5 shared by every agent that acted on it; counts against the last holder in per-server metrics only. **More:** ADR-010, ADR-013.
- **entry agent** — the agent a request first lands on. **Here:** chosen uniformly at random (each agent equally likely), seeded; `entry_rule: uniform` in configs/sim.yaml. **More:** ADR-013; docs/architecture.md.
- **Forward (action 1)** — the agent hands the request to a visible neighbour. **Here:** masked at k = 0 and at the hop limit; the agent decides only whether to forward, not to whom. **More:** ADR-013; docs/guide-errata.md; Guide F2.
- **Forward target** — the neighbour server a forwarded request actually goes to. **Here:** chosen by the environment, not the agent: the visible neighbour minimising expected wait plus this request's estimated service time there, ties to the lowest index. **More:** ADR-013; docs/guide-errata.md.
- **heuristic, local vs global** — each baseline exists in two forms. Local: sees only the same 7 features an agent sees and picks Accept / Forward / Defer (`LocalPolicy.act`), a fair peer for the agents. Global: sees the whole cluster and assigns the request directly (`GlobalPolicy.assign`), an information-advantaged reference. **Here:** global forms define λ_sat. **More:** ADR-012; docs/architecture.md policies.heuristics.
- **hop** — one Forward of a request from one server to another. **Here:** Request.hops, limit `max_hops: 2` in configs/sim.yaml; a hop-count feature is in the observation. **More:** docs/context.md Agent; docs/architecture.md sim.request.
- **JSQ (join shortest queue)** — send each request to the server with the fewest requests waiting. **Weakness:** ignores that servers differ in speed. **Here:** baseline in local and global forms. **More:** docs/context.md Baselines; ADR-012; M1.23.
- **KV term (w_kv)** — a reward penalty for a request served while its server was nearly full of KV cache. **Why:** a nearly full server risks stalling others. **Here:** −w_kv × fraction of the request's resident ticks with KV fullness above 80% (`kv_threshold: 0.8`), credited to the serving agent at resolution. w_kv is not decided: set by a later ADR; M1.24 checks the magnitude against R_SLA first. Replaces "−1 per step". **More:** ADR-014; docs/guide-errata.md.
- **N (cluster size)** — the number of servers, and so of agents. **Here:** N = 4 in two classes. **More:** docs/context.md Environment; configs/servers.yaml.
- **Po2 (power of two choices)** — pick two servers at random and send the request to the less loaded one. **Why it is famous:** it gets most of the benefit of checking every server while looking at only two. **Here:** baseline in local and global forms; the local rule is written in the ADR-012 amendment (M1.21). **More:** docs/context.md Baselines; ADR-012; M1.23.
- **prefix-hit fraction** — what share of this request's prompt a given server could skip because it already holds it in the prefix cache. **Here:** observation feature 7, 0 when the cache variant is off (`prefix_hit_enabled`). **More:** docs/architecture.md Observation; ADR-009.
- **R_SLA** — the reward for the SLA outcome: +10 both targets met, −10 a target missed, −5 dropped. **Here:** credited at resolution to every agent that acted on the request. **More:** docs/context.md Agent; ADR-010; Guide F3.
- **Random and Round-robin** — the two stateless baselines. Random: pick any server uniformly. Round-robin: take servers in turn 1, 2, 3, 4, 1, … **Here:** need no state, so no local/global split. **More:** docs/context.md Baselines; ADR-012; M1.23.
- **server class** — a type of server with its own speed, memory and price. **Here:** fast-expensive and slow-cheap. The count of each is not decided: set by the M0.5.6 ADR; prices and KV budgets likewise. **More:** ADR-003; configs/servers.yaml; M0.5.6.
- **SED (shortest expected delay)** — send each request to the server where it would finish soonest: queue wait plus its own service time there. **Why it beats JSQ:** it accounts for speed, so a fast server with a slightly longer queue can still win. **Here:** the strongest baseline; its global form defines λ_sat and its local form (SED-local) is an approximation using only the neighbour mean, not SED itself. Viva-critical: rewrite from memory (M1.25b). **More:** ADR-011, ADR-012; M1.25.
- **tick (dt)** — one step of the simulator's clock. **Here:** all agents act once per tick, at most one decision each (ADR-013). dt is not decided: set by ADR in M1.2 (configs/sim.yaml `dt: null`); it must be small relative to t_step. **More:** ADR-001, ADR-013; docs/phase-plans.md M1.2.
